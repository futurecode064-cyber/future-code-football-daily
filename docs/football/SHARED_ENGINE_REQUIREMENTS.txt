Endpoint Names များကို Existing Code နှင့် ကိုက်ညီအောင် ပြောင်းနိုင်သည်။

## 4.1 Performance

- Worker CPU အနည်းဆုံးသုံးပါ။
- Prepared SQL Statements သုံးပါ။
- Database Query မလိုအပ်ဘဲ အထပ်ထပ်မလုပ်ပါနှင့်။
- Daily Data ကို Versioned JSON Response ဖြင့် ပေးပါ။
- ETag နှင့် Conditional Requests ကို Support လုပ်ပါ။
- CDN Cache နှင့် Browser Cache ကို သေချာသတ်မှတ်ပါ။
- Large JSON Payload ကို လိုအပ်သလို ခွဲထုတ်ပါ။
- Public/static route များ Worker ကို မလိုအပ်ဘဲ မဖြတ်စေရ။
- API Endpoint တစ်ခုကို Website တစ်ခုတည်းမှ အကြိမ်များစွာ ခေါ်နေခြင်း မဖြစ်စေရ။

## 4.2 Publishing Consistency

Data အားလုံးကို တစ်ပိုင်းစီ Live ထုတ်ခြင်း မလုပ်ရ။

Publication Version တစ်ခုအဖြစ် ပြင်ဆင်ပြီး QA အောင်မြင်မှ Active Version ကို အတူတူပြောင်းပါ။

Main နှင့် Brand Websites များသည် တူညီသော Published Version ကို ဖတ်ရမည်။

Publish ပြီးသည်နှင့် သက်ဆိုင်ရာ Cache ကို Invalidate သို့မဟုတ် Version Change ဖြင့် Refresh လုပ်ပါ။

Cache က ဘယ်လိုအလုပ်လုပ်သည်၊ Data ဘယ်လောက်နောက်ကျနိုင်သည်ကို ရှင်းလင်းစွာ သတ်မှတ်ပါ။

## 4.3 Failure Protection

Workers API သို့မဟုတ် D1 ယာယီ Error ဖြစ်လျှင်—

- Website UI မပျက်ရ။
- Blank Page မပြရ။
- Existing cached validated data ရှိလျှင် ဆက်ပြပါ။
- Data အဟောင်းဖြစ်ကြောင်း Timestamp ဖြင့် ပြပါ။
- မမှန်သော Data အသစ်ကို အစားထိုးမပြပါနှင့်။
- API ပြန်ကောင်းသည့်အခါ Latest Version ကို ပြန်ယူပါ။

Static Pages Website ၏ Availability ကို API Failure တစ်ခုကြောင့် အကုန်လုံး မထိခိုက်စေရ။

# PHASE 6 — PDF IMPORT AND SOURCE VERIFICATION

နေ့စဉ် Football Data အတွက် Existing `FUTURE_CODE_DAILY_MASTER_PROMPT_V3(1).txt` ကို Editorial Specification အဖြစ် အသုံးပြုပါ။

အဲဒီ Prompt ထဲက PDF Fidelity, Research, Writing Style, QA, Date Handling, Preview, Results နှင့် Publication Rules များကို ထိန်းသိမ်းပါ။

## 6.1 Import Workflow

1. Owner က PDF Upload လုပ်မယ်။
2. PDF စာမျက်နှာအားလုံး Extract လုပ်မယ်။
3. Myanmar Font/Unicode ပြဿနာ စစ်မယ်။
4. PDF Rows ကို Source Ledger ထဲ သိမ်းမယ်။
5. Fixture Identity ကို စစ်မယ်။
6. Home/Away နှင့် Odds Giving Team ကို သီးခြားစစ်မယ်။
7. League, Match Time နှင့် Odds စစ်မယ်။
8. Missing/Ambiguous Data တွေကို Flag လုပ်မယ်။
9. Owner က လိုအပ်တာ ပြင်နိုင်မယ်။
10. Validation အောင်မြင်မှ Draft Ready ဖြစ်မယ်။

PDF Parsing ကို Workers Free CPU Limit အတွင်း မလုပ်နိုင်လျှင် Browser-side Processing သို့မဟုတ် ရှိပြီးသား ChatGPT Work Processing ကို အသုံးပြုပါ။

CPU-heavy PDF Processing ကို Worker Request တစ်ခုထဲ အတင်းမထည့်ပါနှင့်။

## 6.2 Data Fidelity

- PDF Row Order မပြောင်းရ။
- PDF မြန်မာအသင်းနာမည်များ မလွဲရ။
- မူလကြေးကို Current Odds အဖြစ် မကူးရ။
- PDF ပြင်ပမှ Match မထည့်ရ။
- ပွဲမရှိသော League ကို မပြရ။
- Original Source Hash သိမ်းရ။

## 10.1 Free Plan Design Targets

လက်ရှိ Free Plan အတွက် အောက်ပါသတ်မှတ်ချက်များကို စစ်ဆေးပါ။

- Pages: 500 Builds/month
- Workers Builds: 3,000 Build Minutes/month
- Workers Runtime: 100,000 Requests/day
- Workers Free HTTP CPU: 10 ms/request
- D1 Read: 5 Million Rows/day
- D1 Write: 100,000 Rows/day
- D1 Storage: 500 MB per Database / 5 GB per Account

စည်းမျဉ်းပြောင်းလဲထားလျှင် Official Documentation ကို အခြေခံပါ။

## 10.2 Daily Build Target

**Normal Daily Content Update = Zero Cloudflare Builds**

ChatGPT က PDF စစ်ရန် ၁ နာရီကြာလျှင် Workers Build Minutes ၆၀ မကုန်ရ။

Daily Data ကို D1 မှာ Update လုပ်ရုံဖြစ်ရမည်။

Code/Function/Design ပြောင်းသည့်အချိန်မှသာ Build လုပ်ပါ။

## 10.3 Limit Monitoring Dashboard

- Workers Requests Today
- Workers CPU Usage
- Workers Build Minutes Used/Remaining
- Pages Deployment/Build History
- D1 Rows Read
- D1 Rows Written
- D1 Storage Usage
- API Errors
- Cache Hit Ratio (ရနိုင်ပါက)
- Last Successful Publication
- Last Successful Backup

Official API က မပေးသည့် Metric ကို အတုမတွက်ပါနှင့်။

မရနိုင်သော Metric အတွက် Cloudflare Dashboard တိုက်ရိုက်ကြည့်နိုင်မည့် Link နှင့် ရှင်းလင်းချက်ပေးပါ။

Limit 70%, 85%, 95% Threshold များကို Dashboard Warning အဖြစ် စနစ်တကျပြနိုင်လျှင် ထည့်ပါ။
